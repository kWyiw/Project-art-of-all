## 0. 这次替换，到底替换掉了什么

| OJ | 你的新体系 | 影响 |
|---|---|---|
| 手牌（回合抽/打） | **没有手牌**。卡是永久持有物，放在卡槽里 | UI 底部的"手牌"整个消失，换成背包栏 + 战斗栏 |
| 每回合打 1 张卡（花星星） | **打牌动作消失**。卡在战斗里自动开火 | 棋盘层少了一个决策，`R-TURN-003` 的"每回合 1 次"随之作废（见 §8.3） |
| 攻/防/闪 掷骰，一次交换定胜负 | **实时冷却，双方同时开火，持续到一方 HP 归零** | 战斗从 5 秒变 15~27 秒 |
| 战斗前各用 1 张战斗卡（隐藏信息） | **战斗前免费重组上场牌**（开战即锁定） | 保留"构筑决策"，但删掉"猜对方用什么卡" |
| 卡牌费用用星星支付 | 卡用**碎片在商店买**，或用奖励格获得 | 碎片仍是"货币 + 分数"双角色，不变 |
| 卡有 1c/2c 占格 | **一维卡槽**，1c/2c/3c 占连续槽位 | 见 §2 |
| 战斗 5 秒、一局 30+ 场 | 战斗 15~27 秒、一局 8~12 场 | ⚠️ 这直接改写了胜场阈值（见规则书 §4.3） |

**最关键的一条架构收益**：OJ 的战斗有"猜对方是否用卡"的隐藏信息，那需要网络同步；你的战斗**开战即锁定、全程零输入**，所以战斗可以是一个**纯函数**：

```csharp
BattleResult ResolveBattle(BattleSnapshot a, BattleSnapshot b, ulong seed);
```

这是整套设计里最值钱的一点——它让 AI 能试算、让平衡工具能离线跑 10 万局、让联机零回滚。**不要为了任何"战斗中操作"放弃它**。

## 1. 两层架构与接口

```
棋盘层（回合制）            战斗层（实时，纯函数）
─────────────────          ─────────────────────────
背包 10c（全部持有）  ──►  战斗栏（上场子集，按等级限宽）
商店 / 奖励格 / 生成器 ──►  装进背包
出售（免费，无限次）  ──►  局外永久成长 / 放置地块陷阱
                           │
                           └─► 全程零输入 → BattleResult
                                │
   ◄──────────────────────────┘
   碎片 ±N、胜场 ±N、HP 变化、消耗品摧毁
```

```
R-IF-001  战斗层是纯函数：输入两个 BattleSnapshot + 一个种子，输出 BattleResult。
          禁止读取棋盘状态、禁止读写背包、禁止访问引擎时间。
R-IF-002  棋盘层是唯一的状态持有者。战斗层只返回"结果"，由棋盘层负责写回。
R-IF-003  战斗时长上限由战斗层内部的超时惩罚裁决（20s 起伤害、60s 硬平局），棋盘层不得干预。
R-IF-004  生命值**只在本场战斗内存在**（棋盘层没有生命值，玩家裁决 v1.4）：
          开战时按双方等级查表得到最大生命（`战斗规则书.md` BT-2.4 / BT-4.7），
          战斗结束即丢弃。中毒/灼烧/护盾等战斗状态同样**不跨战斗**。
          （v1.5 前写的"HP 是棋盘层属性、跨战斗保留"已作废。）
R-IF-005  上场牌在开战瞬间锁定。锁定后任何输入（含断线重连）都不改变战斗过程，
          只重放同一个种子。
```

## 2. 卡槽：一维，不是网格

牌的尺寸写作 `Xc`，注释写的是"占据 X 个卡槽"，且规则里反复出现"最左侧""右侧相邻"——**这是一维序列，不是背包乱斗的二维网格**。这是个好消息：实现和 UI 都简单一个数量级。

```
R-SLOT-001  背包 = 一维卡槽序列，总宽度 10c。卡牌占连续槽位。
R-SLOT-002  战斗栏 = 另一条一维序列，宽度上限随等级：1~4 级 4c，5 级 6c。
            （数值可调，但"随等级增长"这条要保留）
R-SLOT-003  战斗栏的相邻关系**独立于背包顺序**。玩家可以任意重排战斗栏。
R-SLOT-004  1c/2c/3c 的价格基准：1g / 2g / 4g。
R-SLOT-005  「相邻」= 在**当前这条序列**里左右紧邻的牌（不看背包）。
R-SLOT-006  重组战斗栏是免费动作、不限次数；**开战瞬间锁定**（R-IF-005）。
```

> **为什么必须明确 R-SLOT-003**：如果战斗栏的相邻关系继承背包顺序，玩家就会被"背包顺序"绑架，而背包顺序又是购买顺序决定的——这会让"相邻"类构筑彻底不可控。**战斗栏必须可以自由重排**，这是整个相邻系统的可用性前提。

### 2.1 背包生效 vs 上场生效

README 里"草场 2c 放在背包也生效"说明存在两种作用域：

```
R-SLOT-007  每张牌有一个 field Scope：
              BattleOnly  —— 必须装进战斗栏才生效（默认）
              BagAndBattle —— 放在背包也生效（草场、部分地产牌）
              BagOnly     —— 只在棋盘层生效（纯经济牌）
R-SLOT-008  BagAndBattle 的牌若已装进战斗栏，**不重复生效**（取并集，不叠加）。
```

## 3. 时间模型

整个战斗必须用**整数 tick**，禁止用 `float` 的秒累加（否则同一个种子在不同平台上会分出不同胜负）。

```
R-TIME-001  时间基准：60 tick = 1 秒（与规则书的三条铁律一致）。
R-TIME-002  冷却以 tick 计数。`3s` = 180 tick。
R-TIME-003  每 tick 的推进顺序（固定，不得调换）：
              ① 推进所有 CD（应用加速/缓速倍率）
              ② 结算周期性状态（中毒/灼烧/再生）
              ③ 触发所有 t=0 的可用技能（按卡槽序号从左到右）
              ④ 结算护盾吸收 / 死亡判定
              ⑤ 超时惩罚计时器（1200 tick 起，每 6 tick 一次）
R-TIME-004  "可用"= CD 剩余 ≤ 0。触发后 CD 重置为 card.cooldown。
R-TIME-005  加速：CD 推进 ×2；缓速：×0.5。两者同时存在时**先乘后加再取整**
            （具体公式见 R-TIME-008）。
R-TIME-006  充能 N 秒 = CD 剩余直接减去 N×60 tick，下限 0。
R-TIME-007  多重释放 N：本次施法重复 N+1 次（含原 1 次）。
            重复不额外消耗 CD，**每一次重复都完整触发被动**。
R-TIME-008  一 tick 内的 CD 推进量 = floor(1 × 加速倍率 / 缓速倍率)。
            倍率用整数表示：加速 = +100%，缓速 = -50%。
            例：同时加速+缓速 → 净 1.0×。
            ⚠ **玩家裁决（取代本条的"2 层叠乘"）**：加速与缓速按**状态存在性**生效，
              **没有层数**。同种状态再次施加只**刷新持续时间、不叠加效果**。
              所以任何时刻单张牌的速度只可能是 1× / 2× / 0.5×，永远到不了 0.25×，
              也就不需要"层数上限"这种东西。
            见 `战斗规则书.md` BT-3.3 ~ BT-3.5、BT-5.8。
```

> **为什么 R-TIME-003 的顺序要写死**：`①推进CD → ③触发技能` 和 `③触发 → ①推进` 会让"CD 恰好归零"的牌在一场战斗里多打或少打一次。这不是理论洁癖——20 秒的战斗里，3s 的牌会开火 7 次，多一次就是 14% 的差距。**顺序必须固定，并且进测试。**

## 4. 状态效果

你的牌表里出现了 6 种：中毒、灼烧、再生、护盾、格挡、缓速（缓速是 CD 层，见 §3）。其中「护盾」和「格挡」在两张牌上分别出现（汽车门板"护盾"、胶带"格挡"），**语义相同，必须合并**。

```
R-ST-001  护盾：吸收等量伤害，不吸收"无视护盾"的伤害（中毒）。**仅在本场战斗内存在**，战斗结束即消失（玩家裁决 2024-xx）。
R-ST-002  中毒：每秒对持有者造成（层数）点伤害，**无视护盾**。层数可叠加。
R-ST-003  灼烧：每 0.5 秒造成（层数）点伤害，然后层数 -1。
R-ST-004  再生：每秒恢复（层数）点生命（不超过最大 HP）。层数可叠加。
R-ST-005  所有状态在战斗结束时清零。
R-ST-006  中毒/灼烧/再生 的层数在施加时可被"修正"影响（见 §5）。
```

### 4.1 中毒与再生：测量结论 + 已裁决「不加衰减」

> **✅ 已裁决（玩家决定）：中毒与再生按原设计——层数只增不减，战斗结束时才清零。**
> 下文是当时的测量与备选方案，**保留作为记录，不构成待办**。
> 规则口径以 `战斗规则书.md` 的 BT-5.4 / BT-5.6 为准。
> 若日后实测需要收紧，采用的手段是**给每层加 8 秒存活时间**（保住"层数只增不减"的规则形状），而不是加衰减。

按原设计，**中毒没有衰减**，于是它的累计伤害是**平方增长**：

```
层数(t) = 0.625 × t          （核废水 1c 4s 1d4，期望 2.5 层/次）
伤害/s(t) = 层数(t)
累计伤害(T) = 0.625 × T² / 2
```

**一张 1c 的核废水，在 25 秒里打出的伤害是 165~195 点**（HP 只有 100~300）。而作为"基准线"的撬棍（1c 3s 1d6）25 秒只有 **29 点**。**同一价位、同一槽位，差 6 倍。**

| 方案 | 核废水 25s 累计伤害 | 相对撬棍 | 结论 |
|---|---|---|---|
| 现状（无衰减） | **≈165** | **5.7×** | **← 采用（玩家裁决）** |
| 每秒衰减 10% | ≈110 | 3.8× | 否决 |
| 每秒衰减 20% | ≈55~62 | 1.9× | 否决 |
| 每秒衰减 30% | ≈45 | 1.5× | 否决 |

**再生（压缩饼干 1c 3s 1d4）更糟**：它是负中毒，25 秒能奶回 **260 点**，比任何防御牌都强。

**当时的建议（已被否决，仅存档）**：

```
R-ST-007  中毒：每秒造成（层数）点伤害后，层数 ×= 0.8（向下取整）。
R-ST-008  再生：每秒恢复后，层数 ×= 0.7。
R-ST-009  衰减用整数定点，禁止浮点。

→ 裁决结果：R-ST-007 / R-ST-008 不采用。中毒与再生层数只增不减。
   R-ST-009 随之作废（没有衰减运算需要定点化）。
```

> **对照：灼烧为什么不失衡？** 因为灼烧自带 `每 0.5s -1 层`，它天然自我限制。
> 一张火堆（2c 8s 1d4，配 2 个相邻废料 → 3 连释放）期望施放 7.5 层，累计伤害 ≈ 32 点 / 8 秒 = **4 dmg/s**。这是健康的设计：**靠构筑（相邻废料数量）变强，而不是靠平方曲线**。
> **中毒/再生要往这个方向修，而不是调骰子。**

### 4.2 超时裁决（已被玩家规则取代，此处只记录实现口径）

我最初提出的"25s 后双方各受递增伤害、同时受击判平局"已被否决。**玩家裁决的版本如下，它才是唯一权威**（见 `战斗规则书.md` BT-7.1~BT-7.5）：

```
R-ST-010  战斗时长无硬上限，只有两档：
          ① t = 20.0s 起，每 0.1s 结算一次超时惩罚：
               k = 超时后第几次结算（k = 1, 2, 3, …）
               双方各受 (k + 9) / 10 点伤害（整数除法）
               ⚠ 这是**普通伤害**：先扣护盾（R-ST-001），护盾不足才扣生命；
                 不受修正、不可减免、不可闪避、不触发受击类被动
               惩罚伤害导致双方同时归零 → 平局
          ② t = 60.0s：强制结束，判平局，双方无奖励无惩罚
```

> **"不穿盾"是玩家裁决**："只叠盾、不打人、靠超时惩罚耗死对手"必须是一条成立的玩法。实现上它就是一个普通伤害，走已有的 absorb 路径，**不要为它开一条 ignoreShield 分支**。

超时惩罚的累计曲线（用于平衡预估，与 `战斗规则书.md` BT-9.3.2 逐行一致）：

| 超时时刻 | k | 单次伤害 | 累计伤害 | 300 血单位状态 |
|---|---|---|---|---|
| 20.1s | 1 | 1 | 1 | 存活 |
| 21.0s | 10 | 1 | 10 | 存活 |
| 25.0s | 50 | 5 | 150 | 半血 |
| 26.0s | 60 | 6 | 210 | 濒死 |
| 27.0s | 70 | 7 | 280 | 必死 |
| 30.0s | 100 | 10 | 550 | — |
| 40.0s | 200 | 20 | 2100 | — |
| 60.0s | 400 | 40 | 8200 | 硬平局 |

**含义**：300 血、零防御的单位从 20s 起大约 6~7 秒内被惩罚打死。所以**绝大多数战斗在 20~27 秒之间结束**，龟缩 build 会被自己的防御反噬。同时 60s 硬平局给了极端局面一个体面的终点。

> **实现要点**：累计次数 k 用整数递推 `k += 1`，伤害用整数除法 `(k + 9) / 10`。**不要**用浮点现算 `ceil((t - 20) * 10)`——tick 与秒的换算会因浮点误差偶尔跳 1 点，联机复现时分叉。

## 5. 数值修正（Modifier）

你给的注释里有一条极重要的细则，**它决定了整套数值系统的天花板**：

> "修正不会超过骰子上限，即 d6 投出 6 点 +1 修正后还是 6 点，同理 d6 投出 1 点后 -1 修正不会降为 0 点"

```
R-MOD-001  修正作用于**每一枚骰子**，不是作用于总和。
R-MOD-002  修正后 clamp 到 [1, 骰面上限]。所以 1D6+100 恒等于 6。
R-MOD-003  修正来自：卡的固有修正、来自相邻/光环的动态修正、永久修正（局内）。
           全部相加后一次 clamp。
```

> **这条规则有一个漂亮的副作用**：「自噬之蛇 1c 伙伴 / 右侧相邻牌所有数值 +100 修正」在语义上等于 **"右侧相邻牌必定掷出最大骰"**。
> 我建议就按这个意图实现，并**把文案改成「右侧相邻牌的骰值必定最大」**——现在的"+100"会让玩家以为能打出 100 点伤害，实际是被 clamp 掉的，这是纯 UI 欺骗。

```
R-MOD-004  【价值】= 这张牌的售价（同一字段）。默认 1c→1 / 2c→2 / 3c→4，可被卡牌改写（淡水 0g）。
R-MOD-005  【动态价值】如铜锣烧"每回合结束价值+1"、黄金战车"每次出售卡牌价值+1"、
           回收站"废料价值按大小 +1/2/3" —— 价值是一个**可变数值**，
           被 `Xd6`（X=价值）这类表达式读取。
R-MOD-006  作用域分三级，必须显式声明，不得靠"看代码猜"：
             TickScope    单次结算内有效
             BattleScope  本场战斗内有效（如热熔切割器"每次缓速使其骰数+1"）
             RunScope     本局内有效、写存档（如粉碎机"永久+1"、幸运饼干的永久修正）
```

## 6. 词条与光环（Aura）

```
R-AURA-001  词条集合：武器 / 工具 / 废料 / 食物 / 伙伴 / 陷阱 / 地产 / 技艺 / 资源
R-AURA-002  光环在**求值瞬间动态重算**，不在装备时固化。
            理由：火堆的"每与一张废料相邻+1多重释放"会随相邻牌变化、
                  自噬之蛇的 +100 会随重排变化。固化会让"重排战斗栏"这个操作产生歧义。
R-AURA-003  求值顺序：先算所有光环对数值的加成（无先后依赖，求和），
            再算卡牌自身修正，最后 clamp。**光环之间不允许形成链式依赖**
            （A 加强 B、B 又加强 A 这种必须在数据校验阶段就被拒绝）。
R-AURA-004  相邻类选择器共 5 种：
              Self / AdjLeft / AdjRight / AllAdjacent / AllByTag
R-AURA-005  "最左侧""最右侧"按当前战斗栏序列求；为空则该效果不触发（不报错）。
```

> **R-AURA-003 是一条会被违反的规则**：只要允许"光环链"，玩家迟早会拼出 A→B→C→B 的循环，然后数值爆炸或死循环。**在数据导入时做一次有向图环检测**，把环当作加载错误直接拒绝。

## 7. 触发总线（被动效果 = 监听器）

你的牌表里已经有 6 张牌是被动触发的（塑料棚、特种橡胶、磨刀石、胶带、铁丝网、回收站），而且明确写了 **"其主动效果可以触发其被动效果，其他牌对敌人造成缓速也能触发这张牌的被动效果"** —— 这句话定义了整个架构：**主动效果不是"直接做事"，而是"发事件"，被动效果监听事件。**

```
R-EVT-001  所有效果都通过事件总线结算。主动效果 = 发事件；被动 = 订阅事件。
R-EVT-002  事件清单（v1 必须全实现）：
              BattleStart / BattleEnd
              CardCast(cardId, owner)
              DamageDealt(source, target, amount, isPoison)
              DamageTaken
              ShieldGained(amount)
              StatusApplied(kind, layers)   kind ∈ {Poison, Burn, Regen}
              SlowApplied(count) / HasteApplied(count) / ChargeApplied(seconds)
              CardDestroyed
              CardSold                       ← 棋盘层
              TurnEnd                        ← 棋盘层
R-EVT-003  事件派发是**同步、深度优先**的；同一事件的多个监听者按卡槽从左到右。
R-EVT-004  允许"效果触发效果"（塑料棚的自触发），但**单次 Cast 的嵌套深度上限 = 8**，
            超过则丢弃并记警告（防无限递归）。
R-EVT-005  RNG 只在事件处理内消耗，且用**战斗种子派生的独立流**，
            保证"同样的输入 → 同样的随机目标"。
```

### 7.1 关键歧义：随机目标

你的注释说：*"没写明具体哪张牌的加速/缓速/充能效果即为随机选择目标"*。

```
R-EVT-006  随机目标的候选集 = 目标方**当前上场**的牌（不含已摧毁）。
R-EVT-007  候选集为空 → 效果静默失效（不消耗、不报错、不打日志刷屏）。
R-EVT-008  随机取自战斗种子派生的 RNG 流，同一场战斗内递增，跨战斗重置。
```

> **R-EVT-007 需要一个 UI 提示**：玩家看到"巧克力"没反应会以为卡了。建议在战斗日志里给一行灰字"（无可作用目标）"。

## 8. 卡牌数据 Schema

用 CSV 或 YAML 都行，但**必须能表达你现有 33 张牌，且不含任何"每张牌一个 C# 类"**。

```yaml
id: crowbar
name: 撬棍
size: 1                      # c
cooldown: 180                # tick；省略 = 被动牌
tags: [Weapon, Tool]
value: 1                     # g，同时是"价值"
scope: BattleOnly            # BattleOnly | BagAndBattle | BagOnly
active:
  - effect: DealDamage
    amount: { dice: { count: 1, faces: 6 } }
    target: Enemy
passive: []
```

**必须支持的"原子效果"**（覆盖你全部 33 张牌）：

| 类别 | 原子 | 对应你的牌 |
|---|---|---|
| 伤害 | `DealDamage(dice)` | 撬棍、消防斧、粉碎机、黄金战车、法棍 |
| 护盾 | `GainShield(dice)` | 汽车门板、胶带、塑料棚 |
| 状态 | `ApplyPoison/Burn/Regen(dice)` | 核废水、油桶、打火机、火堆、热熔切割器、压缩饼干 |
| 时间 | `Charge/Haste/Slow(count, duration, target)` | 发电机、巧克力、润滑油、混凝土块、铁丝网、塑料棚 |
| 结构 | `MultiCast(+N)`、`DestroySelf`、`DestroyTargetCard` | 自噬之蛇、双持、燃烧瓶、粉碎机 |
| 生命 | `Heal(dice)`、`Lifesteal` | 雪水净化器、淡水、矿泉水、法棍 |
| 成长 | `ModifyValue(±N)`、`AddPermanentModifier(target, ±N)` | 铜锣烧、黄金战车、幸运饼干、淡水 |
| 生成 | `GenerateCard(cardId, to: Bag)` | 雪水净化器 → 淡水 |
| 棋盘 | `PlaceTrap(tile, effect)` | 铁丝网 |
| 光环 | `Aura(selector, stat, ±N)` | 磨刀石、自噬之蛇、回收站、双持 |

**触发订阅**（`passive` 列表）：

```yaml
passive:
  - on: StatusApplied          # 塑料棚：每次触发缓速获得 1D6 护盾
    filter: { kind: Slow, side: Source }
    effect: GainShield
    amount: { dice: { count: 1, faces: 6 } }
```

> **这套 Schema 的验收标准**：用它能把你 33 张牌全部描述出来，且新增一张牌**不需要改 C# 代码**。做不到就是 Schema 漏了原子，去补原子，不要开"这张牌特殊"的口子。

## 10. 数值体检：CD 与战斗时长必须一起定

假设 HP 100~300、战斗自然结束目标 **15~20 秒**（超过 20 秒由超时惩罚收尾）、1D6 期望 3.5：

| 牌 | 槽 | CD | 期望/次 | 期望 DPS | **每槽 DPS** |
|---|---|---|---|---|---|
| 撬棍 | 1 | 3s | 3.5 | 1.17 | **1.17** ← 基准线 |
| 混凝土块 | 1 | 3s | 2.5 + 缓速 | 0.83 | 0.83 |
| 消防斧 | 2 | 6s | 10.5 | 1.75 | 0.88 |
| 汽车门板（盾） | 2 | 9s | 21 | 2.33 | 1.17 |
| 法棍 | 1 | 6s | 3.5伤+3.5疗 | 0.58 | 0.58 |
| 火堆（配 2 废料） | 2 | 8s | 累计 32 灼烧 | 4.00 | **2.00** |
| 粉碎机（首战→8 骰） | 3 | 9s | 4.5 → 36 | 0.50→4.00 | 0.17→1.33 |
| 黄金战车（价值 3→8） | 3 | 12s | 10.5 → 28 | 0.88→2.33 | 0.29→0.78 |
| 核废水 | 1 | 4s | **累计 165** | 6.60 | **6.60** 🔴 |
| 压缩饼干 | 1 | 3s | **累计 260 疗** | 10.4 | **10.4** 🔴 |

**三个结论：**

**① 中毒/再生是唯一的失衡点（但已决定保留）。** 其余牌都在 0.5~2.0 的每槽 DPS 区间内，只有这两张冲到 6.6 和 10.4。**玩家已裁决按原设计保留（§4.1），因此它们的高值是有意为之**——它们换来的是"前 10 秒几乎无威胁"的延迟收益定位。BalanceSim 跑批时把这两张列为重点观测项，而不是预先修正。

**② 12s CD 的牌在 20 秒的战斗里只出 2 次。** 热熔切割器、黄金战车都是 12s，意味着它们只能触发 2 次（t=0,12）；而 3s 的牌触发 7 次（t=0,3,…,18）。**CD 跨度 3~12s 太大。**

> **裁决（v1.5）：玩家未采纳"收窄到 3~10s"的建议，CD 区间维持 3~12s。** 因此上面这条问题的**缓解责任下放到内容侧**，而不是规则侧：
> - 12s 的牌必须按"20 秒打 2 发"来配单次数值（黄金战车初始价值建议给 2，否则成长前太弱）；
> - 新牌不要随手填 11~12s，那个区间在本作里等价于"终结技"；
> - BalanceSim 必须单独输出"每槽每秒伤害"（已含），并用它抓 **CD 与数值不匹配**的牌，而不是改 CD。

**③ 盾与伤是 1:1 平衡的，纯盾流因此可以成立。** 汽车门板 2c 产 2.33 盾/s；2 张撬棍（同 2c）产 2.33 伤/s。**完全相等** → 一个纯盾 build 对上一个纯输出 build，谁也打不死谁，于是**超时惩罚成为决胜机制**。

而玩家裁决"惩罚不穿盾"，所以胜负由**有效生命（生命 + 护盾）**决定：谁的血池更深，谁最后倒下。这把"叠盾"从"拖时间"变成了"一条真的能赢的路线"，同时 60 秒硬平局保证两个纯盾 build 不会无限拖（两边同血池 → 同 tick 双亡 → 平局）。

> **给平衡工具的提醒**：BalanceSim 必须同时输出"有效生命曲线"和"累计伤害曲线"，否则会误判纯盾流。纯盾流在 DPS 表上永远很难看（它不输出），但它在真实对局里能赢。

## 11. 永久成长与"卖牌"经济（最容易失控的一块）

你的牌表里埋了一条很深的构筑轴：

```
幸运饼干  → 卖它，最左侧食物永久 +1 修正
淡水      → 卖它，最左侧恢复牌恢复值永久 +1 修正
黄金战车  → 每卖一张牌，价值 +1
回收站    → 所有废料价值 +1/2/3
粉碎机    → 每场战斗 +1 骰数
铜锣烧    → 每回合 +1 价值
```

也就是说：**"卖牌"不是丢弃，是建造动作**。这是一个很好的机制——它让"低价值废料"变成燃料——但它同时是三个 Bug 的温床：

```
R-ECO-010  每张牌必须有 `permanentBonus` 计数器，写进存档。
R-ECO-011  永久修正**无上限**会让终盘失控。建议总修正上限 = 骰面上限 - 1
            （即 1d6 最多 +5），超过部分不生效但仍在 UI 显示。
R-ECO-012  "售价套利"必须封死：任何情况下 **卖出价 ≤ 买入价**。
            重复买卖不得产生碎片或永久修正的净收益。
            幸运饼干本身也是一张牌，所以"买饼干→卖饼干"每轮净亏 1 碎片，
            这条天然成立，但要在测试里锁住。
R-ECO-013  "回合结束"类被动（铜锣烧、雪水净化器）作用于**棋盘回合**，
            不是战斗回合。理由：战斗中生成牌会破坏 R-IF-001（战斗纯函数）。
R-ECO-014  "出售时"效果每回合最多触发 1 次（铁丝网的陷阱、永久修正），
            防止一回合连卖 3 张把地块变成雷区。
```

## 12. 棋盘层 ⇄ 战斗层的交互清单

| 交互 | 方向 | 规则 |
|---|---|---|
| 抢夺碎片、+胜场 | 战斗 → 棋盘 | 规则书 R-CBT-002 |

| 上场牌锁定 | 战斗内部 | R-IF-005 |
| 消耗品被摧毁 | 战斗 → 棋盘 | **建议：战斗内摧毁的牌，战斗后仍保留在背包**（否则构筑会被一次战斗打散，体验极差）。若你想做"真摧毁"，必须改用"每场战斗临时禁用" |

| 生成牌（淡水） | 棋盘内部 | 回合结束进背包，背包满则按 R-ECO-006 折现 |
| **准备期调阵容（5s）** | 棋盘 → 战斗 | **新裁决**（`战斗规则书.md` BT-2.3.1~2.3.7）：战斗确定发生 → 5.0 秒 `Preparing` 阶段 → 双方只能动战斗栏 → 全体 `SetReady` 或 5s 到 → `CombatStarted`。准备期**不计入战斗 tick**，超时时钟从 BT-2.5 初始化后才走 |
| **对手战斗栏可见性** | 战斗 → 棋盘 | **新裁决**：战斗外可查他人战斗栏；背包永不下发；`Preparing`/`Fighting` 期间双方战斗栏互不可见（BT-2.3.4、UI 规格 §7.3） |

> **"战斗内摧毁"这条我必须强调**：如果 燃烧瓶（摧毁自身）、粉碎机（摧毁废料）的效果在战斗结束后永久生效，那么"打一场仗少两张牌"会让玩家不敢进战斗，整个游戏节奏崩掉。**默认必须是"本场临时禁用"，除非你明确想要一个硬核 roguelike 消耗品经济。**

## 16. 一句话总结

这套卡牌设计本身是**健康的**：相邻光环（磨刀石、火堆、双持）、事件驱动的被动（塑料棚、特种橡胶）、价值成长（黄金战车、铜锣烧）、卖牌造物（幸运饼干、淡水）——四条构筑轴都很扎实，且都是"靠构筑变强"而不是"靠单卡超模"。

**它现在只剩一个"病"**：12s 的 CD 在 20 秒的战斗里出不了几次（热熔切割器一局只出 2 次，黄金战车 2 次）。中毒/再生的高数值已由玩家裁决保留，不算缺陷。
