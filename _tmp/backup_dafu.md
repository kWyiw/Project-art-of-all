> **项目形态（v1.7 定调，影响全文档）**：这是一个**四人派对游戏**，规则一律按"4 名玩家"书写。

## 2. 对我上一版建议的 8 处修正

照抄 OJ 之后，下面这些我之前的判断**错了**，必须改。

### 2.1 🔴 升级不是"消耗"，是"阈值判定"（最重要的修正）

- **我上一版说的**：碎片升级"消耗并清零"。
- **OJ 实际规则**：Norma 是**阈值**——"当玩家的状态满足对应的 Norma 需求，便达成 Norma，并升 1 级"。**星星不会被扣掉。**
- **为什么这个区别是致命的**：如果做成消耗，玩家攒到 120 星星去升级 → 归零 → 立刻失去所有购买力 → 一次升级把你打回赤贫，节奏会非常痛苦；而且"抢 30% 碎片"的惩罚会变得荒谬（你随时在 0 附近）。
- **改为**：

```
在 home 格结算时：
    if (当前等级 < 5 且 碎片 >= Norma[等级].碎片) → 升级，碎片不扣除
    if (当前等级 < 5 且 胜场 >= Norma[等级].胜场) → 升级，胜场不扣除
    if (当前等级 == 5 且 满足任一阈值) → 达成 6 级，胜利
```

- **但张力不会消失**：碎片仍然是商店货币，买珍宝会让你**掉到阈值以下**。这就是 OJ 的核心张力（星星既买卡又是分数），完全保留。

### 2.2 🔴 升级结算可在**任意** home；但「主动停留权」只给自家（**用户裁决，覆盖我上一条建议**）

我上一版（以及 OJ）把两件事绑成一件事：「谁能停」=「谁能升级」。你的规则把它们拆成**两个正交的权限**，这是更精确的设计：

| | 主动停留权（经过时可选择停下） | 恰好到达（骰子走完、终点落在此格） |
|---|---|---|
| 自家 home | ✅ 有 | ✅ 触发升级结算 |
| 别家 home | ❌ 无（不高亮、不可停） | ✅ 触发升级结算 |

落地成两条独立规则（这是要写进代码的东西）：

- **升级结算挂在「地块」上**：`HomeTile` 的 `Owner` 只用于「出生点」与「停留权」，**不参与**「能否升级」的判定。
- **主动停留权挂在「归属关系」上**：`IsStoppableByPass(node, playerId) ⇒ node.IsHome && node.Owner == playerId`。

**我收回**上一版「别家 home 无任何功能」的说法。但要保留一个提醒：这样一圈里就有 **4 个**升级兑现点（而非 1 个），"攒够资源却要跑回家"的等待成本大幅下降 → **Norma 阈值可能需要上调**，见 §4.3 与 §3.7。

用户已裁决 **方案 C**（自家 home 不加数值增益）——理由见 §3.7 的节奏推导：**「可主动停留」这一条本身就已经提供了足够的自家 home 价值**，不需要再叠数值。

### 2.3 🔴 Norma 一旦选定，达成前**不能改**

- **我上一版建议**：允许随时切换升级方式。
- **OJ 实际**："这个 Norma 在达成前，始终持有，无法更改。"
- **改为**：升级那一刻选择下一级的 Norma，锁定。这让"我选胜场路线但现在撞上一堆怪"变成真实的赌博，是这个系统的乐趣来源。**不要给玩家开反悔口子。**

### 2.4 0 级直接砍掉

- **我上一版建议**：0 级 → 1 级免费自动。
- **OJ 实际**：所有人开局 1 级。
- **改为**：**逻辑上开局即 1 级**。"0 级"只作为开场演出（角色从 0 级升起的动画），不进状态机。否则你会有"0 级 HP 为空 / 战斗栏为空 / 能否被攻击"三个必须处理又永远用不到的分支。

### 2.5 🔴 移动的交互模型要改：**预计算高亮格 + 点击直达**

- **我上一版建议**：逐格前进，每个中间节点按优先级弹一次询问。
- **OJ 实际**（截图 4 与规则书）：*"当玩家处于岔路时可自行选择前进的方向。除此之外，系统还会自动算出玩家能够停留的格子（高亮格），点击这些高亮的格子，系统会按照正确的岔路走到这个格子上。"*
- **这个设计比顺序询问好得多**：玩家在掷骰后**一次性看到所有可停留选项**，不用一路点"Yes/No"，也不用在岔路口猜"走下去会不会错过我想要的格子"。
- **改为**：见 §3.4 的预计算算法。这是本作最重要的一条 UX 决策，也直接决定了网络协议（移动命令 = 目标节点，而不是逐格方向）。

### 2.6 战斗奖惩：按单位类型差异化，且比例是 50% 不是 30%

- **我上一版建议**：30%，加上限 20。
- **OJ 实际**：

| 单位类型 | 被击倒时 | 胜者获得 |
|---|---|---|
| 杂鱼（怪物） | 损失**全部**星星 | 胜点 **+1** |
| 玩家 | 损失**一半**星星（向下取整） | 胜点 **+2** |
| Boss | 损失**全部**星星 | 胜点 **+3** |

- **改为**照抄这个结构（碎片按同比例）。**关键点：打赢玩家（+2）比打赢杂鱼（+1）更值**——这是 OJ 把玩家推向 PvP 的核心设计。你 README 里"一律 +1"把这个激励抹平了，PVP 会没人打。

### 2.7 传送：砍掉独立棋盘，改 OJ 式 Warp

- OJ：传送格 → **随机传送到另一个传送格**（WarpMove 则再追加一次移动阶段）。
- 你的 README：传送格 → 进入"由虚空隔离开的独立棋盘"。
- **改为 Warp**。独立棋盘 = 第二张地图 + 第二套状态机 + 进出规则 + 掉落/背包交互 + 存档结构，成本约等于地图层的 40%，而收益只是"一个新房间"。**Warp 能给你 90% 的体验，1% 的成本。**

### 2.8 战败无位移（v1.6 已删除"返回 home"）

**裁决**：战败**不移动**，留在战斗发生的地块上。与 OJ 一致（OJ 被击倒只丢星星）。

**为什么删**：原设计"败者返回自己的 home"要额外约定四件事——返回算不算位移、算不算经过、返回后能否当回合做 home 结算、在自己 home 上被别人打赢时是否也触发。四条都要写、都要测，换来的是一个 OJ 不需要的机制。**收益小于复杂度，删。**

**推论**：停在有玩家的地块上打完一架，**人还在那格**。所以 home 结算与战斗胜负**解耦**——见 R-HOME-007。战败者丢掉的是碎片/胜场，不是位置。

## 3. 正式规则书（编号化，可直接编码）

> 编号规则：`R-<域>-<序号>`。代码注释与测试用例均引用编号。

### 3.1 术语与数值基础

| 术语 | 标识符 | 说明 |
|---|---|---|
| 珍宝 | `Relic` | 卡牌。宽度 `1c/2c/3c` |
| 珍宝碎片 | `Shard` | 唯一货币 + 星星 Norma 的度量 |
| 胜场 | `Wins` | 胜点 Norma 的度量，**不消耗、不为负** |
| 地块 | `Tile` | 图中的节点 |
| 自家 / home 格 | `HomeTile` | 每名玩家 1 个，出生点 |
| 停留 | `Stop` | 移动终点，或主动选择停下 |
| 经过 | `Pass` | 移动途中的中间节点 |
| 应战 | `Engage` | 一次完整的战斗事件入口 |
| Norma | `Norma` | 升级目标，`ShardNorma` 或 `WinsNorma` |

```
R-BASE-001  一局固定 4 名玩家（4 个席位）。
R-BASE-002  所有玩家开局等级 = 1，持有 ShardNorma（角色特例除外）。
R-BASE-003  等级 1~6；等级 6 即胜利，等级 6 不参与战斗。
R-BASE-004  回合数无上限（单机与联机一致，直到有人到 6 级）。
R-BASE-005  席位与规则解耦：一个席位由真人或 CPU 填充，**同一条规则对两者完全一致**。
            阶段 A = 1 真人 + 3 CPU；阶段 B = 4 真人。差异只在"谁提交命令"，
            不在规则、数值、地图、卡池、随机种子分布。
R-BASE-006  CPU 受与真人相同的信息约束（R-CPU-002），禁止读取对手隐藏状态。
```

### 3.2 地图

```
R-MAP-001  地图是**有向图**：节点 + 有向边。只能沿出边前进，不可逆行。
R-MAP-002  节点出边数 = 2 及以上，且被标记为 forkNode 时，该节点是岔路。
R-MAP-003  地图数据须通过 4 项校验：
           ① 每个节点至少 1 条出边
           ② 从任一 spawn 可达全部节点
           ③ HomeTile 数量 = 玩家数，且 owner 唯一
           ④ 传送组至少 2 个成员，且组内互不为同一节点
R-MAP-004  表现坐标（pos）只供渲染，逻辑层禁止读取。
R-MAP-005  每个玩家出生在其 HomeTile 上（OJ 同）。
R-MAP-006  地块 = 基础地块（恒为 Base）+ 0..n 个地块效果（TileEffect）。
           "特殊地块"一律由效果叠加实现，不新增基础类型。
```

### 3.3 回合阶段

```
R-TURN-001  回合顺序按玩家序号 0→1→2→3 循环。
R-TURN-002  一个回合只有两个主动操作：CARD（可选）与 MOVE（必须）。
            其余一切（装配/卸下/查看）为免费动作，不消耗回合。
R-TURN-003  回合内的行动类操作上限：**每回合最多使用 1 张"发动/销毁型"珍宝**
            （对应 OJ 的"每回合使用一张卡"）。装配/卸下不限次。
R-TURN-004  MOVE 阶段结束后结算地块效果，然后进入 TurnEnd。
R-TURN-005  TurnEnd 触发：行动后收益类效果 → 写存档点 → 切换玩家。
R-TURN-006  存档点固定为 TurnEnd。回合中途不存档。
```

> **R-TURN-003 是 OJ 与你的"装配栏"之间唯一的接口，务必想清楚**：OJ 的"卡牌"和你的"珍宝"是不同东西。
> - **装配/卸下**（免费、不限次）= 背包乱斗式的构筑操作；
> - **发动/销毁**（每回合 1 次）= OJ 式的"出牌"，用来放陷阱、换碎片、触发位移。
> 这两件事必须分开计数，否则玩家会在一回合内连续销毁 10 张珍宝刷碎片。

### 3.4 移动（核心算法）

```
R-MOVE-001  掷骰：1D6，值 1~6。
R-MOVE-002  移动从当前节点出发，沿出边前进 k 步（k = 骰子点数）。
R-MOVE-003  【经过】= 中间节点；【停留】= 终点或主动选择的停下点。
            起点不算经过；终点只走"停留"规则，不触发"经过"规则。
R-MOVE-004  主动选择停下（自家 / 与其他玩家交战）后，**本次移动剩余步数作废**。
            （OJ 明示："战斗后停留在该格"）
R-MOVE-005  应战结束后，玩家停在该格，本回合不再移动。
R-MOVE-006  传送（Warp）是**位移**，不是移动：不消耗步数、不触发经过判定、
            不触发终点停留规则（除非目标格本身有可触发效果——见 R-TILE-011）。
```

**关键：可停留格预计算（R-MOVE-003 的实现方式）**

掷骰后，在**移动开始前**就算出玩家所有可以主动停下的节点，并高亮：

```
// 输入：起点 node、剩余步数 k
// 输出：所有"可停留且可达"的节点（含到达路径）
List<Candidate> FindStopCandidates(int playerId, int node, int steps)
{
    void Dfs(int cur, int left, List<int> path)
    {
        if (left == 0) return;
        foreach (var next in OutEdges(cur))
        {
            // 可主动停留候选 = ①自己的 HomeTile ②有其他玩家的节点
            // 关键：别人的 HomeTile **不是**候选、不高亮；
            //       但骰子恰好走到时会正常触发 home 结算（两件事是两个权限）
            if (IsStoppableByPass(next, playerId))
                yield Candidate(next, path + [next], left);
            Dfs(next, left - 1, path + [next]);
        }
    }
    Dfs(node, steps, [node]);
}
```

**这个函数的存在，决定了你的网络协议长什么样：**

```csharp
// ✅ 推荐：移动命令 = 目标节点（或 null = 自由走）
public sealed record MoveCommand(int PlayerId, int? TargetNodeId) : IMatchCommand;

// ❌ 不推荐：逐格方向
// public sealed record ChooseDirectionCommand(int PlayerId, int EdgeId);
```

理由：
1. 玩家点高亮格 → 一次 RPC 说清"我要停在那儿"，服务端自己按路径重放并广播 `StepEntered` 事件。**少 4~6 次往返**。
2. 玩家想在岔路自己走而不停 → 发 `TargetNodeId = null` + 第一次岔路的 `direction`。
3. 断线重连时，"目标和路径"比一串"方向选择"更好恢复。

**UI 契约**（照抄 OJ）：
- 掷骰后进入 `Moving` 状态，界面提示"选择移动方向。"
- 所有 `FindStopCandidates` 结果高亮；同时岔路节点的出边显示为可点击箭头。
- 点高亮格 = 自动按路径走过去并停下；点箭头 = 沿箭头走、不停、继续剩余步数。

## 4. 数值换算表（OJ 的小整数 → 你的量级）

**这是最容易漏掉的一块**：OJ 的数值全是 1~6 的小整数，你的是 100~300 的 HP + 一个碎片经济。凡是 OJ 里出现具体数字的规则，都必须换算，否则会出现"恢复 1 HP 等于没恢复"这种荒谬结果。

> **本节的换算已经按玩家裁决大幅收缩**：因为生命值只存在于战斗内，所有"棋盘层回血"类换算都不需要了（§4.2）。真正需要换算的只剩碎片量级与胜场阈值。

|---|---|---|---|

| Drop 格减量 | `等级 × 骰` → 1~30 | 同 | 你的 Drop 会比 OJ 更狠（因为你碎片更"值钱"），可考虑 `等级 × 骰 × 0.5`，向下取整 |

### 4.2 生命值：棋盘层没有，它属于战斗层 🔴（玩家裁决后重写）

**玩家裁决：生命值只在战斗里用，棋盘层玩家没有生命值。**

这条推翻了 OJ 的一整个子系统（Check 格回血、Heal 格、残血状态），必须在换算表里整段作废：

| OJ 的东西 | 原换算 | 现在 |
|---|---|---|
| Check/Home 恢复 1 HP | 最大 HP 的 20% | **删除**。home 不恢复任何东西，只做 Norma 判定 |
| Heal 格 / Heal ×2 格 | 20% / 40% | **整格删除**（§4.2.1 方案 C） |
| 残血走棋盘的紧张感 | — | 由"战斗内血量"承担，棋盘层永远满状态 |

**生命上限在哪定义？** 它是一条**战斗内参数**，由玩家等级决定（等级越高，战斗内血越厚）：

| 等级 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 战斗内生命上限 | 100 | 150 | 200 | 250 | 300 | — |

### 4.3 胜场阈值（**必须重算，这是错得最隐蔽的一处**）

OJ 的胜场阈值是 1/2/5/9/14，累计 **31 场**才能靠胜场路线升到 6 级。这个数字成立的前提是：**OJ 一局能打 30+ 场战斗**（战斗格 + 玩家互撞，且每场战斗只有 1~2 次掷骰，5 秒结束）。

你的战斗是**珍宝 CD 自动战斗**，一场 15~27 秒（20 秒后开始吃超时惩罚，极少打满 60 秒）。同样 31 场，光战斗就要 8~14 分钟，而且中间还得移动、买货。**直接照抄会让胜场路线变成不可能完成的任务。**

（v1.5 追加：PvP 每场另有 **5 秒准备期**（R-CBT-009），但胜场路线的主力是打杂鱼，PvE 的准备期通常被「立即开战」一键跳过，所以这个估算基本不变。）

**换算方法**：

```
目标：胜场路线的总时长 ≈ 碎片路线的总时长
已知：碎片路线累计需要 Σ(15+40+80+130+210) = 475 碎片
假设：每完整轮约 3.5×4=14 格移动，平均一圈 9 回合，
      每圈可获得 ≈ 60 碎片（Bonus 格 + 奖励折现 + 抢夺），
      则 475 碎片 ≈ 8 圈 ≈ 72 回合 ≈ 一局 25~35 分钟
要求：胜场路线也约 8 圈内达成
      8 圈内你能主动发起的战斗次数 ≈ 每圈 1 次（怪物格 3~4 个 + 玩家相遇）
      → 总胜场阈值应 ≈ 8~10 场
```

**建议阈值（比 OJ 低一半以上）**：`1 / 2 / 4 / 6 / 8`，累计 21 场。这个数字必须用 BalanceSim 验证，**它是你第一个要跑的数值实验**。

**⚠️ 因 home 规则变更必须复算的第二处**：上面推导假设"一圈 1 个升级兑现点"。你的规则下**一圈有 4 个**（4 个 home 全都能结算），所以"攒够 475 碎片却要等跑回自己家"的等待成本基本消失，升级会来得更早更顺。

- 建议阈值先按**上调 15%** 起测：`17 / 46 / 92 / 150 / 240`。
- 在 BalanceSim 里做成一个开关 `HomeUpgradeAllOwners = true/false`，两种都跑，比较：
  - 平均对局轮数
  - 碎片"囤积浪费量"（达到阈值后到兑现之间累计的碎片溢出）
  - 4 名玩家的升级时间点方差（如果任意 home 可升级，方差应该显著变小 → 运气的影响降低，这是好事）
- **这一条同时决定胜场路线要不要跟着调**：4 个兑现点意味着"胜场路线"的兑现速度也变快了，两条轨道仍要对齐。

OJ 无背包上限（10 张卡组 + 无限手牌）。你加了 10c 上限 → 这是纯粹的原创规则，见 R-ECO-006。**建议同时加一个"背包满时进入奖励格"的体验兜底**：至少给玩家一个"用新换旧"的选项，否则攒满背包后奖励格全变成折现，快感归零。

### 补充：已裁决 **方案 C** —— 自家 home 不加任何增益

**裁决理由（这条规则的节奏推导）：**

设地图一圈 N 个节点（建议 N = 32），移动用 1D6。

| 来源 | 每圈可用的升级判定次数 | 说明 |
|---|---|---|
| **自家 home** | **≈ 1 次**，且基本"想停就能停" | 见下方证明 |
| 别家 home ×3 | ≈ 0.28 × 3 ≈ **0.84 次** | 只能骰子恰好踩中；一圈落脚 ≈ N/3.5 ≈ 9 次，踩中特定节点概率 ≈ 9/32 ≈ 0.28 |
| **合计** | **≈ 1.8 次 / 圈** | |

**"自家 home 想停就能停"的证明**（这是 C 方案能成立的关键）：

> 一圈内你必然经过自家 home 一次。而「可停留窗口」= home 前 6 个节点，宽度是 6，恰好等于最大骰子点数。所以**你不可能从窗口外一步跳过整个窗口**——某次移动的起点必然落在窗口内。而起点落在窗口内 ⇒ 本次移动的任一 ≤6 步位置都是合法停留候选 ⇒ 一定能停在 home。

所以「可主动停留」这一条**本身就已经把自家 home 变成"每圈一次的稳定兑现机会"**，和"别家 home 只能靠运气"形成了约 1 : 0.84 的价值差。这个差已经足够，**不需要再叠数值增益** —— 这就是选 C 的理由。

**由此推出的节奏基准（可直接用于验证阈值表）：**

```
升到 6 级需要 5 次升级
最少圈数 = 5 / 1.8 ≈ 2.8 圈   ← 资源完全不设限时的理论下限
实际圈数 ≈ 6~8 圈             ← 受碎片/胜场阈值约束
```

这与我 §4.3 里"一局约 8 圈、25~35 分钟"的假设一致，说明阈值表 `17/46/92/150/240` + `1/2/4/6/8` 的量级是对的。**BalanceSim 要验证的第一个数字就是"实际圈数是否落在 6~8"，偏离就调阈值。**

**对地图设计的两条硬约束**（由 C 方案直接决定）：

1. 4 个 home 应把环**四等分**（N=32 → 节点 0/8/16/24）。因为 home 现在是可以互相替代的升级点，均匀分布能把"离最近 home 的最远距离"压到最小，避免出现"半圈没有升级点"的死区。
2. home 位置**决定玩家节奏**：出生在 home 上 ⇒ 每圈一次的稳定兑现节奏是相同的；不要出现"某个 home 前面是连续 3 个 Warp 格"之类导致兑现率异常的布局。
3. **C 方案的隐含好处（不需要补偿数值的原因之一）**：落后玩家不会因为离家太远而卡在"攒够了却兑不了"，追赶更顺。这是"任意 home 可升级"这条规则的真正价值。
